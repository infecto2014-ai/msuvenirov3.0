# Схема распределения задач (Agent Routing)

Обновлено 12.11.2026 (промты владельца «Skills и стандарты качества» и «Система специализированных агентов»). Правила моделей — `docs/MODEL_POLICY.md`. Определения агентов — `.claude/agents/*.md`. Проверка состава и моделей — `node scripts/check-agents.mjs`.

## 1. Кто главный

**Главный управляющий — главная сессия на Fable 5.2** (проверено: модель доступна). Он ставит задачи, выбирает исполнителя, проверяет результат, принимает ключевые решения, согласует спорное с владельцем, делает коммиты. Агенты между собой не общаются и друг друга не вызывают — всё идёт через главную сессию.

Если главная сессия запущена не на Fable, ключевые решения принимает запасной агент `project-director` (Fable).

## 2. Состав агентов

Шесть специалистов (по заданию владельца) и три вспомогательных. Вспомогательные нужны, чтобы рутина не уходила на дорогую модель — этого требует политика моделей («Не используй Opus для простых и повторяемых задач»).

| Агент | Модель | Обязанности | Может менять | Инструменты |
|---|---|---|---|---|
| `project-auditor` | Sonnet 5.5 | Аудит проекта и исходного контента, инвентаризация, сверка нового сайта с аудитом | документы аудита, `docs/audit-data/**`, `scripts/audit/**` | чтение, Bash, запись новых файлов |
| `creative-director` | Opus 5.5 | Креативная концепция, визуальное направление, дизайн-система, глубокая критика дизайна | `docs/design/**`, дизайн-токены, прототипы концепций | чтение, запись, правка, Bash (скриншоты) |
| `ux-architect` | Opus 5.5 | Структура, навигация, сценарии, формы, поведение калькулятора и сметы, план аналитики | `USER_SCENARIOS.md`, `ANALYTICS_PLAN.md`, `docs/ux/**` | чтение, запись, правка |
| `seo-specialist` | Opus 5.5 | SEO-архитектура и оптимизация: карта сайта, запросы, перелинковка, метаданные, разметка, перенос адресов | `SITE_MAP.md`, `SEO_KEYWORD_MAP.md`, `INTERNAL_LINKING_PLAN.md`, `docs/seo/**` | чтение, запись, правка, Bash, поиск |
| `frontend-engineer` | Opus 5.5 | Техническая реализация: архитектура фронтенда, сложные компоненты, калькулятор, смета и заявка, сложные анимации | код сайта (файлы из задачи) | чтение, запись, правка, Bash |
| `qa-reviewer` | Sonnet 5.5 | Тестирование, визуальная проверка, чек-листы качества; код не исправляет | только `docs/qa/**` | чтение, Bash, запись отчётов |
| `frontend-builder` *(вспомогательный)* | Sonnet 5.5 | Типовые страницы и стандартные компоненты по утверждённому образцу, простые исправления, обычные тесты | код сайта (файлы из задачи) | чтение, запись, правка, Bash |
| `content-editor` *(вспомогательный)* | Sonnet 5.5 | Перенос текстов и данных, брифы страниц по готовой структуре, метаданные по готовой стратегии, вычитка | `PAGE_CONTENT_BRIEFS.md`, файлы контента из задачи | чтение, запись, правка |
| `project-director` *(запасной)* | Fable 5.2 | Ключевые решения, если главная сессия не на Fable | ничего (только чтение) | чтение |

Ни у одного агента нет инструментов `Agent`, `SendMessage`, `Skill`: создавать и вызывать агентов, запускать скилы как команду они не могут. Новый агент добавляется только с разрешения владельца — и одновременно в список `EXPECTED` скрипта проверки, иначе проверка падает.

Переименования относительно первой версии (12.11.2026): `content-auditor` → `project-auditor`; `seo-strategist` → `seo-specialist`; `component-builder` + `test-writer` → `frontend-builder`; `content-migrator` + `seo-filler` → `content-editor`. Проверка сборки и обычные тесты — у `qa-reviewer` и `frontend-builder`.

## 3. Какая задача кому

| Задача | Исполнитель |
|---|---|
| Сборка, тесты, проверка ссылок, sitemap, конфигурации агентов | скрипт, без агента |
| Правка в 1–2 местах, перенос файла, запись решения владельца | главная сессия сама |
| Инвентаризация, сверка «было — стало», подсчёты | `project-auditor` |
| Три концепции, дизайн-система, оценка «выглядит ли как работа сильной команды» | `creative-director` |
| Сценарий, навигация, форма, состояния калькулятора | `ux-architect` |
| Структура адресов, запросы, метаданные-шаблоны, разметка, переадресации | `seo-specialist` |
| Заполнение метаданных и текстов страниц по готовым шаблонам | `content-editor` |
| Архитектура кода, калькулятор, смета, заявка, сложная анимация, трудная ошибка | `frontend-engineer` |
| Типовая страница по утверждённому образцу, простой компонент, простая ошибка | `frontend-builder` |
| Проверка готового: сборка, скриншоты 1440/390, чек-листы | `qa-reviewer` |
| Выбор концепции, стека, спор между направлениями, утверждение этапа | главная сессия (Fable) |
| Изменение того, что согласовал владелец | только владелец |

## 4. Порядок передачи задачи

1. Главная сессия определяет сложность (`MODEL_POLICY.md`, раздел 2) и исполнителя по таблице выше.
2. В задаче агенту: цель; **точный список файлов, которые можно менять**; 1–3 документа для чтения; критерий готовности; какой скил применить (если нужен).
3. Отчёт агента — в едином формате: сделано / проверено / не сделано / вопросы владельцу / эскалация.
4. Главная сессия проверяет результат сама (сборка, тесты, выборочная сверка, скриншот), при вёрстке и дизайне — отдаёт на `qa-reviewer`.
5. Запись в `docs/MODEL_USAGE_LOG.md`. Коммит и отправку делает только главная сессия.

## 5. Параллельная работа и файлы

- Один файл в один момент меняет один агент. Владелец каждого документа — в таблице раздела 2; чужой документ агент не правит, а пишет предложение в отчёте.
- Параллельно запускаются только независимые задачи с непересекающимися списками файлов. Все агенты сразу без необходимости не запускаются.
- Зависимые задачи идут по очереди: структура → запросы → брифы; концепция → дизайн-система → вёрстка → проверка.
- Проверяющий (`qa-reviewer`) запускается после исполнителя, а не одновременно с ним.

## 6. Эскалация

| Откуда | Куда | Когда |
|---|---|---|
| `project-auditor`, `qa-reviewer`, `frontend-builder`, `content-editor` (Sonnet) | Opus-агент направления | 2 неудачные попытки, сложная неоднозначность, нужно архитектурное решение |
| `creative-director`, `ux-architect`, `seo-specialist`, `frontend-engineer` (Opus) | главная сессия (Fable) | меняется общая стратегия или несколько согласованных решений |
| главная сессия | владелец | решение отменяет согласованное владельцем |

Направления: `frontend-builder` → `frontend-engineer` (логика, вёрстка) или `creative-director` (вид); `content-editor` → `seo-specialist` (метаданные, структура) или `ux-architect` (тексты форм и сценариев); `qa-reviewer` → `creative-director` (качество дизайна) или `frontend-engineer` (техническая причина); `project-auditor` → `ux-architect` или `seo-specialist` по теме.

Агент сам не эскалирует: возвращает отчёт с пометкой `ЭСКАЛАЦИЯ → …`, дальше решает главная сессия.

## 7. Скилы: кто и когда применяет

Скилы лежат в `.claude/skills/` (источники и лицензии — `RESOURCE_LICENSES.md`). **Разрешение владельца (13.11.2026): без отдельной просьбы скилы применяются только при разработке дизайна сайта** — концепции, дизайн-система, прототипы, вёрстка и её проверка. В остальных работах — только по прямой просьбе владельца. Агент применяет скил, только если это прямо написано в задаче. Правила скилов не отменяют решения владельца, `ANTI_AI_SLOP.md` и `DESIGN_BRIEF.md`.

| Скил | Этап | Кто |
|---|---|---|
| `frontend-design` | концепции, первые экраны, новые страницы | `creative-director`, `frontend-engineer` |
| `ui-ux-pro-max` | подбор палитр, шрифтовых пар, UX-правил при разработке дизайн-системы | `creative-director`, `ux-architect` |
| `impeccable` | критика и доводка готового макета или страницы | `creative-director` (оценка), `qa-reviewer` (режим аудита) |
| `web-design-guidelines` | проверка готового кода интерфейса | `qa-reviewer` |
| `ux-writing` | тексты кнопок, форм, ошибок, подсказок | `ux-architect`, `content-editor` |
| `seo` | техническая проверка страниц перед запуском | `seo-specialist`, `qa-reviewer` |

Чтобы не дублировать: создаёт — `frontend-design`; справочник — `ui-ux-pro-max`; критикует — `impeccable`; проверяет по чек-листу — `web-design-guidelines`. Один и тот же макет двумя «критикующими» скилами подряд не гоняем.
